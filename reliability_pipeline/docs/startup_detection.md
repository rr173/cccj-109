# 离线启机过程识别器（startup 子包）

`startup` 子包直接读取 DuckDB 中的标准遥测测量（`tele_samples`，由
`telemetry` 子系统接入），按一份**固定的 JSON 启机配方**识别每一次启机
尝试，输出三态判定（`confirmed` / `rejected` / `indeterminate`）与可复核
证据。它只回答「这次启机过程是否按配方完成」：**不推断故障结局、不计算
可靠性曲线、不经过压缩归档**。命令行入口：`python3 -m startup.cli`。

```bash
./run_startup_demo.sh            # 一条命令：真实接入 → 识别 → 证据回溯 → 交叉核对
```

## 1. 配方（JSON，计算前校验）

```json
{
  "name": "demo-start",
  "channels": {
    "pressure":    {"channel": 1, "unit": "kPa", "max_age_ns": 1000000000},
    "vibration":   {"channel": 2, "unit": "m/s", "max_age_ns": 1000000000},
    "temperature": {"channel": 0, "unit": "°C",  "max_age_ns": 2000000000}
  },
  "thresholds": {"P_start": 100.0, "P_run": 90.0, "V_run": 5.0, "T_max": 80.0},
  "durations":  {"C": 2000000000, "H": 3000000000, "W": 10000000000}
}
```

- 三个角色（pressure / vibration / temperature）各指定**通道号**与**预期
  单位**，通道号不得重复；每通道 `max_age_ns` 为正整数（零阶保持有效期）；
- 阈值 `P_start`（压力触发）、`P_run`（稳定压力下限）、`V_run`（振动下限）、
  `T_max`（温度上限）必须为**有限**数值；
- 时长 `C`（确认等待）、`H`（连续稳定时长）、`W`（尝试总期限）为正整数
  纳秒，且 `C<=W`、`H<=W`；
- 任何非法（缺项、多余键、非整数时长、非有限阈值、通道重复……）都在
  **计算之前**报错（CLI 退出码 2），不产生任何结果。

## 2. 测量语义：零阶保持与未知

- 每个读数自其整数 `ts_ns` 起**零阶保持**，直到下一次更新或自身
  `ts_ns + max_age_ns`；**过期点起为未知**（保持区间为 `[ts, ts+max_age)`），
  不插值，也不会把很久以前的温度沿用下来；
- **到期与刷新同刻时先采用新更新**（同刻到期不造成空档）；
- 同一通道同一时刻出现多条读数：**值与单位全部相同**才算一次合法更新
  （保留全部来源定位键）；**相互冲突或单位与配方不符** → 该通道转为未知，
  直到之后一次合法更新；
- 状态按 `(device_id, boot_seq, 通道)` 隔离；**布局号不参与状态键**——布局
  更换但通道与单位仍匹配时，零阶保持状态不清空；
- 同一时刻所有通道的更新**先一起生效，再统一判定**，结果不随数据库行
  顺序改变（同刻读数按集合判定，不逐行应用）。

## 3. 启机尝试的生命周期

1. **越线建候选**：压力由「已知且 `< P_start`」变为 `>= P_start` 时建立
   候选，越线时刻为 `s`。**前一个压力值在 `s` 时必须仍未过期**（
   `s - ts_prev < max_age`）；从未知（无读数/已过期/冲突）直接变高不算
   越线。每次越线都建候选——前一次尚未结束也照常建立（候选可重叠，
   各自独立计时）。
2. **确认**：候选等待振动在**闭区间** `[s, s+C]` 内首次达到 `V_run`
   （`s` 时刻已满足也算确认）。窗口错过则该候选不可能成功，但**仍观察
   温度至总期限**，以区分资料完整的失败与资料缺失。
3. **稳定完成**：确认后寻找 `压力>=P_run 且 振动>=V_run` **连续成立 H**
   的最早完成时刻 `c`（允许确认时刻本身开始计时，要求 `c <= s+W`）。
   两项条件有一项为假**或未知**都打断连续计时，恢复后重新累计。
   完成点当刻条件必须仍成立：**恰好过期不能成功**；同刻刷新后仍满足
   则可以。
4. **温度**：候选存活期间温度达到 `T_max`（`>=`）→ **立即 rejected**
   （在完成点当刻升至上限也优先拒绝）。判 `confirmed` 要求 `[s, c]`
   全程温度已知且严格低于 `T_max`。

### 判定结果（三态，每条都带原因码）

| 状态 | 原因码 | 含义 |
|---|---|---|
| `confirmed` | `stable_completed` | 找到最早稳定完成时刻 c，且 [s, c] 温度全程已知且低于上限 |
| `rejected` | `temperature_exceeded` | 存活期间温度达到上限（立即） |
| `rejected` | `confirm_timeout` | 到总期限未确认，且窗口内无参与判断的未知状态（资料完整的失败） |
| `rejected` | `stable_timeout` | 确认后到总期限无连续 H 稳定段，且无参与判断的未知状态 |
| `indeterminate` | `temperature_unknown_before_completion` | 已找到最早 c，但此前安全温度有未知区间（在 c 结束） |
| `indeterminate` | `confirm_timeout_unknown` / `stable_timeout_unknown` | 超时，但窗口内存在参与判断的未知状态，无法区分真实失败与资料缺失 |
| `indeterminate` | `observation_incomplete` | 分析截止早于候选期限且候选尚未结束——**观察未结束，不能报超时** |

**`indeterminate` 不算设备启动失败**：它表示证据不足或观察未完。

### 参与未知判定的范围（固定）

- **温度**：整个存活期 `[s, end]`；
- **振动**：确认窗口 `[s, s+C]` 内；
- **压力与振动**：确认之后（`[confirm, end]`）；
- 确认窗口错过后：只继续观察温度（窗口后的压力/振动未知不参与）。

## 4. 事件驱动的计算方式

这是**按事件时刻推进**的计算，不把纳秒区间展开成逐时刻网格，也不对
每个候选反复扫描整库：

- 每个 `(device_id, boot_seq)` 组**独立流式扫描一次**有序测量批次
  （SQL 按 `ts_ns` 升序，同刻行按集合一起判定）；
- 定时事件进最小堆：读数**过期**（`ts+max_age`，按读数版本作废）、
  **确认窗口关闭**（`s+C`）、**稳定完成检查**（连续段起点 `+H`，按段版本
  作废）、**总期限**（`s+W`）；主循环取「下一测量时刻 / 堆顶」的较小者
  推进；
- **同刻处理顺序**：① 到期（过期点起为未知；同刻刷新随后覆盖，等价于
  刷新优先）→ ② 本时刻全部通道更新一起生效 → ③ 稳定条件跳变（打断/
  重新开始累计）→ ④ 越线建候选 → ⑤ 温度超限（所有存活候选立即
  rejected，优先于完成/期限）→ ⑥ 确认 → ⑦ 确认窗口关闭 →
  ⑧ 稳定完成（当刻条件仍成立才算）→ ⑨ 总期限；
- 分析截止 `analysis_end_ns` 之后的事件不处理；截止时仍存活的候选输出
  `observation_incomplete`。

**未知状态的传播**：每个角色通道维护「未知区间日志」（起因：无读数 /
过期 / 冲突 / 单位不符，含源定位键）。候选判定时按 §3 的固定范围查询
这些区间：完成判定只看温度区间，超时判定看温度 + 窗口内振动 +
确认后压力/振动。

**内存开销**：每时刻只有 O(1) 的通道状态（3 个角色）+ 存活候选数
（任意时刻通常只有最近一个 W 窗口内的越线）× O(1) 候选状态（阶段、
确认时刻、当前连续段起点与版本）+ 本组未知区间日志（与事件数同阶）。
候选之间不共享计时器，越线/回落/再越线产生的重叠候选各自独立得出结论。

## 5. 输出与证据

每次运行落库（`startup_` 前缀，与 `tele_*`、`pipeline` 表共存）：

| 表 | 内容 |
|---|---|
| `startup_runs` | 运行参数：配方 JSON、analysis_end_ns、三态计数 |
| `startup_attempts` | 每次尝试：越线 s、确认时刻、稳定段起止（c-H, c）、结束时刻、三态、原因 |
| `startup_evidence` | 证据时间片（点或半开区间）：越线/确认/打断/完成/温度未知/超温/冲突/期限/截断 |
| `startup_evidence_refs` | 证据引用的源测量定位键 `(file_id, frame_offset, ordinal)` |

证据至少能回答：**确认用了哪条读数**（confirm 证据的引用）、**连续段
为何被打断**（stable_break 证据：低于阈值/过期/冲突，含责任读数）、
**温度未知或超限从哪里开始**（temperature_unknown 区间 /
temperature_exceeded 时点）。**同刻冲突能找到冲突双方**（conflict 证据
引用全部来源行）；**缺测标明时间区间**（未知区间证据，不伪造源样本——
区间类证据可以没有引用行，或只引用导致过期的真实读数）。任何引用都可
沿 `(file_id, frame_offset)` 回到源文件的确切字节。

公开查询命令：

```bash
python3 -m startup.cli run --db DB --recipe recipe.json \
    --analysis-end-ns 1700000025000000000 --run-id r1 [--jsonl out.jsonl]
python3 -m startup.cli attempts --db DB --run-id r1 [--status confirmed]
python3 -m startup.cli evidence --db DB --run-id r1 \
    --device 7 --boot-seq 1 --attempt-seq 1
python3 -m startup.cli verify --db DB --recipe recipe.json --analysis-end-ns ...
```

结果同时可导出 JSONL（`run --jsonl`）。

## 6. 独立参考判定器与核验

`startup.reference` 是与生产状态机**刻意不同路线**的小规模参考实现：
不维护状态机，先把每个角色整理成事件表，用二分查找直接求任意时刻的
零阶保持值，再**枚举事件断点**（全部测量时刻、合法读数过期时刻、
候选派生时刻 s/s+C/s+W/确认时刻/段起点+H）逐个候选独立判定。它不导入
`startup.engine`，期望答案不由生产状态机生成。

核验体系（`tests/test_startup.py` + `verify` 子命令 + demo 自检）：

1. 手工算定的边界用例：正常完成、确认/完成恰好落在期限端点、越线前值
   差 1ns 过期（算）与恰好过期（不算）、完成点恰好过期（失败）与同刻
   刷新（成功）、同刻乱序/冲突/重复/单位不符、重叠候选不同结论、短温度
   缺口 vs 真实超温、分析截断、跨 boot_seq 隔离、布局更换状态连续；
2. 40 个随机种子的引擎 vs 参考逐条比对（含冲突/重复/单位不符注入）；
3. 演示（`run_startup_demo.sh`）：设备 7 由**真实二进制接入命令**
   （`python3 -m telemetry.cli ingest`）生成测量后再识别，逐条核对判定
   与来源定位键；其余小例子直接建库；两个库都跑引擎 vs 参考交叉核对。
